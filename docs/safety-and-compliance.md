# Safety and compliance

*Status: design stance plus a regulatory map, 2026-10-07. This is not legal or EHS advice. Have a regulatory consultant review it before any GxP sale.*

## 1. Stance: an aid, not a safety system

voicelab **helps a trained person follow their lab's procedures.** It is not a safety system, an engineering control, or a substitute for the chemical hygiene plan, safety data sheets (SDS), training, or the PI's judgment. The rules that follow from this:

- **Nothing that keeps people safe depends on voicelab working.** If the server, mic or network fails, the lab is exactly as safe as it was without us.
- **The safety screen is best-effort and narrow.** It catches a known list of dangerous combinations and practices *that are spoken aloud*. It will miss things. We say so in the UI, the onboarding, and the contract.
- **The LLM never has the last word on numbers or hazards.** Calculations come from deterministic tools. Range checks come from the SOP spec. Hazard alerts come from deterministic rules. Claude explains, navigates and converses.
- **The human confirms what gets recorded.** Critical numbers are read back and confirmed before they go into the record.

## 2. Deterministic guardrails

### Pipeline position

```
mic → STT final → normalize → [SAFETY SCREEN] → (wake-phrase gate) → Claude + tools → numeric provenance check → TTS
                                     │                                                     │
                                     └── danger alert: TTS preempts, alert pinned ──────────┘
```

The screen runs on **every** final utterance, including ones not addressed to the assistant, and it runs **before** the LLM. A danger finding:

1. Speaks immediately, preempting any in-flight assistant speech.
2. Pins an alert that needs acknowledgement.
3. Writes a `safety.alert` event with `ruleId`, matched terms and the transcript.
4. Is injected into Claude's context as a system message, so the model doesn't contradict it.

### Rule families (v1)

| Family | Examples | Matching |
|---|---|---|
| Incompatible pairs | Hypochlorite (bleach) + acids, ammonia, or **guanidinium salts** (GITC releases HCN); sodium azide + acid (HN₃), or + copper/lead drains; cyanide + acid; nitric acid + organics; piranha + organics | Alias dictionary per chemical class ("bleach", "Clorox", "sodium hypochlorite", "hypo"). Pairs can match across the current utterance, the last N utterances, and **the current SOP step's reagents and waste stream** |
| Unsafe practices | Mouth pipetting; eating or drinking at the bench; phenol, chloroform or β-mercaptoethanol outside a hood; recapping needles; working with the BSC sash above the mark | Phrase patterns with negation handling ("don't mouth pipette" must not fire) |
| Severe-hazard handling | The current step uses a reagent with H300/H310/H330 (fatal), H314 (corrosive), or H340/H350/H360 (CMR) codes | Fires a PPE or hood reminder once per step, not on every mention |
| Implausible numbers | A volume larger than the named vessel; a concentration above the stock | Done in the calculator tools, not the screen |

### Known limits (publish these)

- **It only hears speech.** It cannot see what you do, check what's in a bottle, or measure quantities.
- **STT errors propagate.** If "guanidine" is transcribed as "gasoline", the guanidine rule misses. To mitigate, the SOP context supplies the reagents even when they aren't spoken, and we report rule recall measured on STT output, not on clean text.
- **Paraphrase and slang** ("the pink waste", "the column stuff") are only caught where they are added as SOP aliases.
- **Coverage is a curated list, not chemistry.** There is no reactivity model. Unknown pairs pass silently.
- **Alert fatigue is a real failure mode.** Target fewer than one false positive per 4-hour run in pilot. Measure it and prune rules that are noisy.

### Testing

- Each rule gets positive and negative fixtures (paraphrases, negations, near-misses), run in CI.
- Run a replay corpus of pilot transcripts, with consent, for false-positive rate and for recall on scripted hazardous utterances read aloud in real lab noise.
- The rule-set version is stamped into every run record.

## 3. Hallucination controls

| Risk | Control | Deterministic? |
|---|---|---|
| Model does math in its head | The system prompt requires calculator tools. Because Claude Opus 5.5 rejects forced `tool_choice`, we add a **numeric provenance check**: every number+unit the assistant is about to *speak* must match (a) a tool result from this turn, (b) the current SOP step text, or (c) the user's own utterance. If it doesn't, the sentence is withheld and the model is re-prompted to call the tool. | Yes (the check) |
| Unit confusion (µL/mL, mM/M) | Calculators are dimension-checked and reject ambiguous input. Spoken output is rendered from the tool result, never generated by the model ("twenty-five microliters"). | Yes |
| Answers not grounded in the SOP | Answers cite step IDs from the structured SOP. On `critical: true` steps, the model may answer **only from the SOP**. Elsewhere, general lab knowledge must be labelled ("general guidance, not from your SOP"). | Partly |
| Confident answers to things the SOP doesn't cover | "Not in the SOP" behaviour: say so, offer to log the question for the SOP owner, never invent a substitution | Prompt + eval |
| Misheard numbers | Low word-confidence numbers trigger "Did you say fifteen, one-five?". **Read-back plus "confirm"** before any critical number or measurement enters the record. | Yes (the gate) |
| Out-of-range readings | Range check against the `measurements[].min/max` spec; the LLM only *explains* the flag | Yes |
| Prompt injection in source SOPs | SOP PDFs are converted to YAML by Claude, then **reviewed and approved by a human** before use; SOP text is treated as data, never as instructions; approved SOPs are versioned and hashed | Process |
| Model drift | Pin the model ID; rerun the calculation, grounding and safety evals on every model or prompt change; record model and prompt versions in each run | Process |
| Silent failure | STT or LLM timeout → "I didn't catch that." The assistant never guesses. Offline mode shows SOP text and timers only. | Yes |

## 4. Regulated environments

## 5. Always-on microphones in shared labs

**The tension:** the safety screen wants to hear everything, while privacy wants only addressed speech to leave the bench.

| Mode | What leaves the device | Use |
|---|---|---|
| **Push-to-talk** (foot pedal or big button) | Only PTT audio | **Default in shared labs and in pilot** |
| Hands-free with wake phrase, screening in the cloud | All speech goes to cloud STT; non-addressed transcripts are screened and then **discarded** unless a rule fires | Pilot, with explicit consent from everyone in the room |
| Hands-free with on-device VAD, wake phrase and a local first-pass screen | Only addressed speech, plus safety-triggered snippets | Target for production |

**Requirements:**

- **Consent** from everyone who may be recorded, not just the operator. Post signage at the bench, show a visible "listening" indicator, and provide a one-tap mute. Run a GDPR DPIA for EU sites, and consult works councils where they exist (per-person telemetry is performance monitoring).
- **Retention defaults:** no raw audio stored. Addressed transcripts and events are kept in the customer-owned run log. Non-addressed transcripts are dropped after screening. Retention is configurable per org, and we support export and delete.
- **Per-person telemetry is aggregate by default.** Individual-level step timings are visible to the individual. Exposing them to managers needs an explicit org policy.
- **Vendor features off:** no emotion or sentiment analysis, no voice cloning of staff, no diarization-based identification.

## 6. IP and confidentiality

SOPs, reagent choices and spoken observations are trade secrets and unpublished results. Treat every vendor as a processor and configure the strictest retention we can:

| Vendor | Strictest option | Notes |
|---|---|---|
| Anthropic (Claude) | Zero data retention for qualifying orgs. Claude Opus 5 is available under ZDR, and Opus 5.5 is documented as unchanged from Opus 5 ⚠ (confirm in writing). | Claude Fable 5.1 *requires* 30-day retention, so don't route ZDR customers to it. A BAA is available for the API ([secondary summary](https://intuitionlabs.ai/articles/is-claude-hipaa-compliant)). |
| Deepgram | `mip_opt_out=true` (no training use, loses the 50% discount); self-hosted for air-gapped sites | Get written retention timelines for opted-out requests |
| ElevenLabs | Zero Retention Mode (`enable_logging=false`), enterprise only | Harder to debug; not available on all products |
| AssemblyAI | Self-hosted streaming ($20k commitment); EU residency | Retention terms for the speech APIs not confirmed |
| OpenAI (experiments only) | ZDR or Modified Abuse Monitoring + BAA | Don't send customer SOPs during experiments |

For our own systems: encryption in transit and at rest, per-tenant isolation, a subprocessor list in the DPA, EU region pinning when required, and no use of customer data for training or cross-customer analytics without a written opt-in.

## 7. What a GxP validation package would need

Assume a CDMO QA team asks "can we use this in a GMP lab?" Before saying yes, the package needs:

1. **Intended-use statement and GxP impact assessment, per feature.** Navigation and conversation: advisory, non-GxP. Calculators and range checks: GxP-relevant if their output is recorded. Run record: GxP record if it is the original.
2. **Supplier assessment pack:** QMS overview, SDLC, SOC 2 report, pen test summary, subprocessor list including model vendors.
3. **URS → functional/design spec → configuration spec**, with a **traceability matrix**.
4. **Risk assessment (FMEA)** including LLM-specific hazards (wrong number spoken, ungrounded answer, missed safety rule, STT mishearing) and the controls from sections 2–3.
5. **Verification evidence:**
   - Exhaustive calculator test suites, including units and edge cases.
   - Safety rule fixtures.
   - Audit-trail tests: immutability, timestamps, user attribution.
   - E-signature tests if we sign.
   - Access control, backup/restore, data export.
6. **Performance qualification for probabilistic parts:** predefined acceptance criteria (for example numeric-token STT accuracy, grounding accuracy on an SOP question set) and ongoing monitoring.
7. **Part 11 / Annex 11 compliance matrix**, clause by clause.
8. **Change control covering third parties:** pinned model and API versions; a vendor model deprecation triggers an impact assessment and regression evals before rollout.
9. **Operational SOPs:** system use, administration, SOP authoring and approval (including review of Claude's PDF→YAML conversion), incident and deviation handling, periodic review, training records.
10. **Record retention and archival** consistent with the predicate rule (for example GLP archives under 21 CFR 58.195), plus deployment qualification (IQ) for VPC or on-prem installs.

## 8. Checklist

**Before pilot**
- [ ] UI, onboarding and pilot agreement state "aid, not a safety system"
- [ ] Safety rules v1 with fixtures in CI; false-positive and recall measured on recorded lab audio
- [ ] Numeric provenance check enforced; calculator output rendered to speech deterministically
- [ ] Read-back + confirm on critical steps, calculations and measurements
- [ ] PTT default; consent form and signage for everyone in the room; mute control
- [ ] No raw audio retention; non-addressed transcripts dropped
- [ ] Vendor retention set: Anthropic ZDR (or confirmed retention terms), Deepgram `mip_opt_out`, ElevenLabs ZRM if eligible
- [ ] Human review and approval of every converted SOP; SOP version hash in each run
- [ ] Model ID, prompt version and rule-set version stamped in every run record

**Before paid (non-GxP) customers**
- [ ] DPA and subprocessor list; EU region option; DPIA template for customers
- [ ] Per-lab configurable safety rules reviewable by the Chemical Hygiene Officer
- [ ] Export and delete of run data; retention configuration
- [ ] Eval suites (calculations, grounding, safety, STT jargon) gating every release
- [ ] SOC 2 Type I started

**Before GxP customers**
- [ ] Decide what the original record is (confirmed transcript vs audio) per customer
- [ ] Append-only audit trail meeting §11.10(e); time sync; user attribution through SSO
- [ ] E-signature flow (§11.50/11.70/11.100–300), or a signing hand-off to a validated ELN or eBR
- [ ] Deterministic workflow mode where the LLM is advisory only (Annex 22 posture)
- [ ] Validation package (section 7) and a supplier audit readiness pack
- [ ] Self-hosted or VPC deployment option with IQ documentation
